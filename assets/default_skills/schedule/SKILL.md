# Schedule — 工作计划管理技能

> SCHEDULE.md 是你的工作记忆。框架会自动将当前计划注入到对话上下文中，
> 你只需在合适时机**使用工具更新它**。

## 核心机制（框架自动行为）

### 自动注入计划摘要

框架会在以下时机自动注入 SCHEDULE.md 的精简摘要到对话上下文：

1. **首轮对话**：100% 概率注入（让你一开始就看到计划）
2. **每 5 轮强制注入**：确保计划不被遗忘
3. **关键词触发**：用户消息包含"计划/进度/任务/schedule/todo/接下来/下一步"等词时立即注入
4. **随机注入**：其他轮次有 50% 概率注入

**注入内容**：
- 待办统计（P0/P1/P2 各多少项）
- P0 任务完整列表（紧急，必看）
- P1 任务前 5 项（重要）
- 工具使用提示

**因此你不需要主动调用 `schedule_load`**（除非需要查看完整详情，如所有 P2 任务或已完成记录）。

### 自动完成检测

框架会监测你的工作并提醒你标记完成：

1. **监测实质性工作**：检测你是否调用了 `toolshell_write`、`toolshell_exec`、`toolshell_run_python` 等工具
2. **分析完成信号**：扫描你的回复中是否有"已完成/搞定/done/fixed/implemented"等词
3. **匹配任务关键词**：将完成信号与待办任务的关键词进行匹配（至少匹配 2 个关键词）
4. **主动提醒**：如果检测到可能完成的任务，会注入提醒消息：`[Schedule 提醒] 你刚才的工作似乎完成了计划中的任务: "xxx"...`

**但你仍应主动标记完成**，不要完全依赖提醒：
- 提醒只是辅助，可能不准确
- 完成任务后应立即调用 `schedule_complete`
- 主动性是高效工作的关键

## 何时使用 Schedule

### ✅ 应该使用的场景

- **多步骤复杂项目**（如"重构整个模块"、"实现新功能"）
- **长期目标**（需要跨多轮对话，无法一次完成）
- **用户明确要求**（"帮我做个计划"、"列出待办事项"）
- **有多个并行任务**（需要优先级管理）

### ❌ 不需要使用的场景

- **一次性简单问题**（"帮我写个排序函数"）
- **探索性对话**（"聊聊 React 的优缺点"）
- **单一明确任务**（"修复这个 bug"，步骤清晰，一轮搞定）
- **纯咨询类问题**（"这段代码有什么问题？"）

## 工作流程

### 1. 收到大型需求时 → 拆解并录入

**步骤**：
1. **理解需求**：确认用户想要什么
2. **拆解任务**：分解成独立的、可验证的子任务
   - 粒度：单个任务应该在 1-3 轮对话内完成
   - 独立：每个任务可以独立验证
   - 明确：任务描述清晰，不含糊
3. **评估优先级**：
   - P0：阻塞后续任务、用户强调紧急、影响核心功能
   - P1：重要但不紧急、有依赖但不阻塞
   - P2：优化、完善、可延后
4. **调用 `schedule_add_task`**：逐条插入（不要一次性添加所有，边添加边思考）
5. **向用户确认**：展示计划，询问优先级和顺序是否合适
6. **开始执行**：从最高优先级（P0）的第一项开始

**示例**：
```
用户：帮我重构这个用户管理模块
你：好的，让我先分析一下需求...
   [分析代码结构、识别问题]
   我建议拆分为以下任务：
   1. P0: 分析现有代码结构，识别主要问题
   2. P1: 设计新的模块架构
   3. P1: 重构数据层（models + repository）
   4. P1: 重构业务逻辑层（services）
   5. P1: 更新 UI 层调用
   6. P2: 编写单元测试
   7. P2: 优化性能
   
   [调用 schedule_add_task 添加这些任务]
   
   计划已录入，我会从 P0 开始执行，是否需要调整优先级？
```

### 2. 执行任务中

**当前任务处理**：
- 专注完成当前任务，不要跳跃
- 遇到依赖问题时，标记当前任务状态（用 `schedule_update` 添加备注 `— 等待 xxx`）
- 如果发现当前任务需要拆分，先完成已开始的部分，再添加新子任务

**选择下一个任务**：
1. 先完成所有 P0 任务
2. 再按顺序处理 P1 任务
3. P2 任务在有空时处理，不主动提起

**处理中断**：
- 用户提出新的 P0 问题 → 立即切换，标记当前任务为"暂停"
- 用户提出 P1/P2 问题 → 告知"已加入计划，当前任务完成后处理"
- 用户要求优先处理某个任务 → 用 `schedule_update` 调整优先级

**汇报进度**：
- P0 任务全部完成时
- 阶段性里程碑（如完成某个模块）
- 用户主动询问时
- 调用 `schedule_review` 生成报告 + 人类友好的总结

### 3. 完成任务后 → 立即标记

**必须立即做**：
1. 调用 `schedule_complete(task_match: "任务前缀或关键词", summary: "简要总结")`
2. 向用户汇报完成情况
3. 告知下一步计划

**不要拖延标记**，原因：
- 避免遗忘
- 保持计划与实际进度同步
- 方便回顾和统计

**示例**：
```
[完成重构数据层]
你：数据层重构已完成，主要改动：
   - 统一了 model 命名规范
   - 抽象了 repository 接口
   - 添加了错误处理
   
   [调用 schedule_complete(task_match: "重构数据层", summary: "统一命名+抽象接口")]
   
   下一步：P1 - 重构业务逻辑层，预计需要 2-3 轮对话。
```

### 4. 工作中发现新问题 → 即时插入

**判断优先级**：
- **P0**：阻塞当前任务（如依赖库缺失、环境问题、严重 bug）
- **P1**：影响后续任务（如设计缺陷、需要提前处理的依赖）
- **P2**：优化改进（如代码风格、注释、文档）

**处理流程**：
1. 评估问题的紧急程度
2. 调用 `schedule_add_task` 插入（指定 `after` 参数控制位置）
3. 告知用户："发现了 xxx 问题，已加入计划，优先级 P1"
4. 决定是否立即处理：
   - P0 → 立即处理，暂停当前任务
   - P1/P2 → 记录后继续当前任务

**示例**：
```
[在重构业务逻辑时发现数据层有 bug]
你：发现数据层的事务处理有问题，这会影响业务逻辑的正确性。
   
   [调用 schedule_add_task(task: "修复数据层事务处理 bug", priority: "P0")]
   
   这是 P0 阻塞性问题，我先修复这个再继续业务逻辑重构。
```

### 5. 用户问进度 / P0 完成时 → 汇报

**调用 `schedule_review` 生成进度报告**，包含：
- 各优先级待办数和完成数
- 完成率统计
- 下一步建议

**然后用人类友好的方式展示**：
```
你：当前进度汇报：

   ✅ 已完成 3 项任务：
   - [P0] 分析现有代码结构
   - [P1] 设计新的模块架构
   - [P1] 重构数据层
   
   🔄 进行中：
   - [P1] 重构业务逻辑层（预计还需 1-2 轮）
   
   📋 待办 4 项：
   - [P1] 更新 UI 层调用
   - [P2] 编写单元测试
   - [P2] 优化性能
   - [P2] 完善文档
   
   整体进度：43%（3/7 完成）
   预计还需 4-5 轮对话完成所有 P1 任务。
```

## 工具使用指南

### `schedule_load` — 加载完整计划

**何时使用**：
- ❌ **几乎不需要**：框架已自动注入摘要
- ✅ 需要查看所有 P2 任务
- ✅ 需要查看已完成记录
- ✅ 需要确认某个任务的详细备注

**参数**：
- `path`（可选）：默认 `SCHEDULE.md`

### `schedule_add_task` — 添加新任务

**何时使用**：
- 收到需求，拆解子任务
- 工作中发现新问题
- 用户提出新要求

**参数**：
- `task`（必需）：简洁明确的任务描述（不要写技术细节）
- `priority`（必需）：P0/P1/P2
- `after`（可选）：插入到某个任务之后（用于控制顺序）
- `tags`（可选）：如 `['feature', 'bugfix', 'refactor']`
- `note`（可选）：依赖关系、阻塞原因、注意事项

**注意**：
- 避免重复添加：先检查是否已有相似任务
- 任务粒度适中：不要太细（"添加一个变量"）也不要太粗（"完成整个项目"）
- 描述明确：让用户和未来的你都能理解

### `schedule_complete` — 标记完成

**何时使用**：
- 完成一个任务后立即调用
- 框架提醒时确认并调用
- 用户确认某个任务已不需要时（也可以用 `schedule_delete`）

**参数**：
- `task_match`（必需）：任务文本的前缀或关键词（前 20 字符用于匹配）
  - 支持模糊匹配
  - 如果有多个匹配项，会选择第一个
  - 建议用任务描述的前几个字
- `summary`（可选）：完成情况简要总结

**示例**：
```dart
schedule_complete(
  task_match: "重构数据层",
  summary: "统一命名规范，抽象 repository 接口"
)
```

### `schedule_update` — 更新任务

**何时使用**：
- 需求变更（修改任务描述）
- 优先级调整（发现某个 P1 任务变成阻塞性 P0）
- 添加备注（标记依赖、阻塞原因、进度状态）

**参数**：
- `task_match`（必需）：要更新的任务的前缀或关键词
- `new_priority`（可选）：新优先级
- `new_text`（可选）：新的任务描述
- `new_note`（可选）：新的备注（不是追加，是替换）

**示例**：
```dart
// 标记当前任务为"进行中"
schedule_update(
  task_match: "重构业务逻辑",
  new_note: "进行中，已完成 60%"
)

// 提升优先级
schedule_update(
  task_match: "修复数据库连接",
  new_priority: "P0"  // 从 P1 提升到 P0
)
```

### `schedule_delete` — 删除任务

**何时使用**：
- 任务取消（用户不需要了）
- 任务重复（与其他任务合并）
- 任务无效（需求变更，不再需要）

**与 `schedule_complete` 的区别**：
- `complete`：任务完成，留下完成记录
- `delete`：任务取消，不留记录

**参数**：
- `task_match`（必需）：任务前缀或关键词
- `reason`（可选）：删除原因（不写入文件，仅日志记录）

### `schedule_review` — 生成进度报告

**何时使用**：
- 用户问进度
- P0 全部完成，汇报阶段性成果
- 长时间对话后的总结

**参数**：
- `path`（可选）：默认 `SCHEDULE.md`

**返回内容**：
- 待办统计、完成统计
- 完成率
- 下一步建议

**注意**：工具返回的是结构化数据，你需要用人类友好的方式重新组织后展示给用户。

### `schedule_archive` — 归档已完成任务

**何时使用**：
- 已完成区域超过 50 条记录
- 用户要求清理历史
- 项目结束，做最终归档

**参数**：
- `days`（可选）：已完成超过多少天的任务会被归档，默认 7 天
- `path`（可选）：默认 `SCHEDULE.md`

**效果**：
- 符合条件的已完成任务移动到 `SCHEDULE_ARCHIVE.md`
- 保持主文件简洁

## 优先级规则

| 级别 | 含义 | 处理原则 | 示例 |
|------|------|----------|------|
| P0 🔴 | 阻塞性/紧急 | 立即处理，不可被打断。多个 P0 按添加顺序或依赖关系处理。 | 环境配置问题、严重 bug、阻塞其他任务的依赖 |
| P1 🟡 | 重要但不紧急 | P0 完成后按顺序执行。是项目的主要任务。 | 功能实现、重构、测试 |
| P2 🟢 | 一般/可延后 | 有空再做，不主动提起。除非用户询问。 | 代码优化、文档完善、额外功能 |

### 多个 P0 的处理顺序

1. **依赖关系优先**：如果 P0-B 依赖 P0-A，先做 A
2. **阻塞范围优先**：阻塞更多任务的先做
3. **用户强调优先**：用户明确要求先做哪个
4. **添加顺序**：其他情况按添加顺序

### 工作中途发现 P0

- **立即切换**：暂停当前任务，用 `schedule_update` 添加备注 `— 暂停，处理 P0: xxx`
- **完成 P0 后回来**：恢复之前的任务

## 任务管理最佳实践

### 任务描述

✅ **好的描述**：
- "重构用户认证模块的数据层"
- "修复文件上传时的内存泄漏"
- "添加用户导出 CSV 功能"

❌ **不好的描述**：
- "修复 bug"（太模糊）
- "把 UserRepository 改成单例模式并添加缓存机制还要处理并发访问"（太长太细）
- "这个函数有问题要改一下"（不明确）

### 标签使用

**建议的标签**：
- `#feature` — 新功能
- `#bugfix` — bug 修复
- `#refactor` — 重构
- `#test` — 测试
- `#docs` — 文档
- `#perf` — 性能优化
- `#security` — 安全相关

**用法**：
```dart
schedule_add_task(
  task: "添加用户权限检查",
  priority: "P1",
  tags: ["feature", "security"]
)
```

### 备注使用

**适合写在备注里的内容**：
- 依赖关系："依赖数据层重构完成"
- 阻塞原因："等待用户提供 API 文档"
- 进度状态："进行中，已完成 60%"
- 注意事项："需要通知前端修改调用方式"

**不适合写在备注里的**：
- 技术实现细节（应该写在代码注释或设计文档中）
- 长篇大论（备注应该简短）

### 任务粒度

**合适的粒度**：
- 1-3 轮对话可以完成
- 可以独立验证
- 有明确的完成标准

**太细**：
- "添加一个变量"
- "写一个 getter 函数"
→ 这些应该是完成某个任务的步骤，不是独立任务

**太粗**：
- "完成整个项目"
- "重构所有模块"
→ 应该拆解成多个子任务

### 避免重复

**添加任务前检查**：
- 框架注入的摘要中是否已有类似任务
- 如果不确定，调用 `schedule_load` 查看完整列表

**发现重复时**：
- 如果完全重复，不添加新任务
- 如果部分重复，合并或拆分

## 注意事项

### 不要在 SCHEDULE.md 中记录技术细节

❌ **错误**：
```markdown
- [ ] 修复用户认证 bug — 问题在 line 234，需要把 if (user == null) 改成 if (user?.isValid != true)
```

✅ **正确**：
```markdown
- [ ] 修复用户认证 bug `#bugfix` — 空指针检查不完整
```

**原因**：
- SCHEDULE.md 是任务列表，不是技术文档
- 技术细节应该写在代码注释、设计文档或 issue tracker 中
- 保持计划简洁，方便快速扫描

### 单个文件的规模控制

- **待办区**：没有硬性限制，但过多时考虑优先级是否合理
- **已完成区**：建议不超过 50 条，超出时用 `schedule_archive` 归档

### 与用户的沟通

**主动汇报**：
- P0 全部完成
- 阶段性里程碑
- 发现重大问题需要调整计划

**征求确认**：
- 添加任务后展示计划，询问是否合适
- 优先级调整时说明原因
- 计划大幅变更时解释影响

**格式化输出**：
- 不要直接输出 `schedule_review` 的 JSON
- 用 emoji、分组、统计数据让报告更易读
- 突出重点（下一步做什么、还剩多少）

## 框架行为总结

**你不需要做的**：
- ❌ 主动调用 `schedule_load`（框架自动注入摘要）
- ❌ 担心计划被遗忘（框架定期注入）
- ❌ 手动检测任务完成（框架会提醒，但你仍应主动标记）

**你需要做的**：
- ✅ 收到需求时拆解任务并录入
- ✅ 完成任务后立即标记
- ✅ 发现新问题时即时插入
- ✅ 用户问进度时调用 `schedule_review` 并友好展示
- ✅ 主动汇报重要进展

**记住**：框架是辅助，你仍是任务管理的主导者。主动性和责任感是高效工作的关键。
